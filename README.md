# عقار لايت

نظام بيع الوحدات العقارية بالتقسيط، لعدة شركات تطوير عقاري على نظام واحد (Multi-tenant).

> **حالة العمل:** الفيتشرز الأربع جاهزة: الأساس (الدخول والجلسات، عزل الشركات، الصلاحيات، سجل التدقيق)، والوحدات والعملاء، والحجز ومسودة العقد، والاعتماد والأقساط والدفعات. ومعها اختبار E2E بـ Playwright للبيع كاملًا.

---

## التشغيل

المطلوب: Docker مع Compose v2. لا حاجة لملف `.env`.

```bash
git clone <repo-url> aqar-lite
cd aqar-lite
docker compose up --build
```

افتح <http://localhost:3000> في **Chrome أو Firefox** (السبب في [الافتراضات](#الافتراضات)).

ماذا يحدث عند التشغيل:

1. تقوم قاعدة البيانات، وسكريبت أول تشغيل ينشئ دور التطبيق `aqar_app`.
2. خدمة `migrate` تطبّق الـ migrations وتزرع بيانات التجربة **بحساب مالك الجداول**، ثم تنتهي.
3. التطبيق يبدأ بعدها ويتصل **بدور `aqar_app` فقط**.

للبدء من الصفر: `docker compose down -v`.

### حسابات التجربة

كلمة المرور لكل الحسابات: **`Aqar@2026!`**

| الشركة | الدور | البريد |
|---|---|---|
| شركة الأفق للتطوير العقاري | مدير الشركة | `manager@ofuq.test` |
| | محاسب | `accountant@ofuq.test` |
| | مندوب مبيعات | `rep1@ofuq.test` · `rep2@ofuq.test` |
| شركة المدار العقارية | مدير الشركة | `manager@madar.test` |
| | محاسب | `accountant@madar.test` |
| | مندوب مبيعات | `rep1@madar.test` · `rep2@madar.test` |

بيانات التجربة في كل شركة: **24 وحدة** في ثلاثة مشاريع، و**4 إلى 5 عملاء لكل مندوب**، وحالة من كل نوع في البيع:
- **مسودة عقد** بانتظار اعتماد المحاسب (عند `rep1`).
- **عقد معتمد** بخصم 3% بدأ قبل 45 يومًا: الدفعة الأولى مدفوعة، والقسط الأول مدفوع نصفه و**متأخر**، وفي سجل التدقيق اعتماده ودفعتاه.
- **حجز نشط** بلا عقد بعد، و**حجز منتهٍ** عادت وحدته متاحة.

وللتجربة أيضًا:
- العميل «محمد السالم» عند `rep1@ofuq.test` في ملاحظاته `<script>` عمدًا، ليظهر كنص.
- نفس رقم جواله مسجّل أيضًا عند `rep2@ofuq.test`: مندوبان قد يعرفان الشخص نفسه، وكلٌّ يرى نسخته فقط.

الـ seed يكتب كل جزء (الشركات والمستخدمون، وحدات كل شركة، عملاء كل مندوب، بيوع كل شركة) فقط إن كان فارغًا، فتشغيله مرة ثانية لا يكرر شيئًا، وقاعدة بيانات من نسخة سابقة تكتسب الجديد فقط. والبيوع تُكتب **عبر الخدمات نفسها** التي يستخدمها التطبيق، فتمر بنفس القواعد: الأقفال، وحد الخصم، والجدول، والتدقيق.

**جولة سريعة:** ادخل بـ `rep1@ofuq.test` ← «الوحدات» ← وحدة متاحة ← «احجز الوحدة» ← «إنشاء مسودة عقد». ثم اخرج وادخل بـ `accountant@ofuq.test` ← «العقود» ← المسودة ← «اعتماد العقد» ← «تسجيل دفعة».

### التطوير المحلي

يحتاج **Node 22.19 أو أحدث** (مكتبة `undici` التي تعتمد عليها Testcontainers تشترط ذلك).

```bash
cp .env.example .env
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d db   # قاعدة البيانات على 127.0.0.1:5433
npm ci
npm run db:migrate && npm run db:seed
npm run dev
```

### الاختبارات والفحوص

```bash
npm run lint
npm run typecheck
npm run test:unit
npm run test:integration   # يحتاج Docker: يشغّل Postgres حقيقي عبر Testcontainers
npm audit --audit-level=high
scripts/smoke.sh           # على نظام شغّال: يدخل عبر نموذج الدخول الحقيقي ويفحص الاستجابة نفسها

# E2E على نظام شغّال (docker compose up)، وأول مرة: npx playwright install chromium
npm run test:e2e           # المندوب يحجز وينشئ المسودة، والمحاسب يعتمد ويسجّل دفعة (بنقرة مزدوجة)
```

`scripts/smoke.sh` يفحص ما لا يظهر إلا على مستوى HTTP، بإرسال النماذج الحقيقية كما يفعل متصفح بلا JavaScript:
- أكواد الحالة، وخصائص الكوكي، ورفض الجلسة بعد الخروج.
- من يفتح أي صفحة: 404 حقيقي للمندوب على سجل التدقيق وصفحات إضافة الوحدات وتعديلها، وللمحاسب على تعديل العملاء والوحدات، ولمندوب على عميل مندوب آخر، ولمدير شركة على وحدات الشركة الأخرى وعملائها.
- أن فلاتر غير صالحة في الرابط لا تكسر الصفحة، ومعرّفًا غير صالح يعطي 404 لا 500.
- أن `ownerUserId` مُهرّبًا في نموذج إضافة عميل يُرفض ولا يُنشئ شيئًا.
- أن الملاحظات التي فيها HTML (من الـ seed ومن نموذج حقيقي) تعود مُهرّبة ولا تُنفَّذ.

الـ CI (`.github/workflows/ci.yml`) يشغّل lint و typecheck والاختبارات و `npm audit`. وفوقه وظيفة تشغّل `docker compose up --build` على جهاز نظيف، ثم تنتظر `/api/health` وتشغّل `scripts/smoke.sh` ثم اختبار Playwright على النظام نفسه.

**ما تثبته اختبارات التكامل في البيع** (Postgres حقيقي، وطلبات متزامنة فعلًا، لا محاكاة):
- 8 مندوبين يحجزون الوحدة نفسها في اللحظة نفسها: ينجح واحد، والسبعة يأخذون رسالة واضحة. الاختبار يحبس الطلبات خلف قفل حتى يتأكد من `pg_stat_activity` أنها كلها تنتظر، ثم يطلقها معًا.
- 5 نسخ من نموذج الدفعة نفسه معًا: دفعة واحدة. و4 دفعات مختلفة معًا، كل اثنتين منها تتجاوزان المتبقي: تنجح واحدة فقط.
- الحجز ينتهي بعد 72 ساعة بلا تدخل، وتعود الوحدة متاحة في أول قراءة.
- مجموع الجدول يساوي السعر النهائي بالهللة في 1000 حالة عشوائية (اختبار وحدة).
- قاعدة البيانات وحدها، حتى بحساب المالك: العقد المعتمد لا يتغير، والدفعة لا تُعدَّل ولا تُحذف، والدفعة التي لم تُوزَّع كاملة على الأقساط تُرفض عند الـ commit.

    clients/    خدمة العملاء وActions
    reservations/  الحجز، وانتهاؤه (expiry.ts)، والمنظّف الدوري (sweeper.ts)

    db/         المخطط، الاتصال، withTenant، الترقيم

  components/   عناصر الواجهة المشتركة: الحقول مع رسائل الخطأ، الشارات، الجداول، الترقيم، نافذة التأكيد، العدّ التنازلي، حالات الفراغ والتحميل والخطأ

### كيف يُضمن أن كل استعلام مقيّد بشركة الجلسة

على أربع طبقات، والأدنى منها يعمل حتى لو فشلت الأعلى:

1. **الشركة لا تأتي من الطلب أبدًا.**
   - السياق الوحيد للتنفيذ `TenantCtx` يُبنى من الجلسة فقط: `tenantOf(session)`، أو داخل `createAction`.
   - لا يوجد مخطط Zod يقبل `companyId`.
   - مخططات الإدخال `strictObject` ترفض أي حقل غير معرّف (حماية من mass assignment).
   - مخططات الـ query في الروابط تُسقط المفاتيح المجهولة.
2. **كل استعلام يخص شركة يعمل داخل `withTenant(ctx)`**، ويفلتر صراحةً بـ `ctx.companyId`.
3. **Row-Level Security في PostgreSQL** هي شبكة الأمان تحت الكود.
   - التطبيق يتصل بدور `aqar_app`، وهو ليس مالك أي جدول، فالسياسات تنطبق عليه.
   - `withTenant` يضبط `app.company_id` و`app.user_id` و`app.role` بـ `set_config(..., true)` على مستوى المعاملة فقط، فلا يتسرّب شيء لمستخدم الاتصال التالي في الـ pool.
   - سياسة العملاء تزيد على الشركة شرط الملكية: المندوب يرى ويكتب عملاءه فقط، والمدير والمحاسب يرون عملاء الشركة. وبلا دور مضبوط لا يظهر عميل واحد.
   - استعلام نُسي فيه شرط الشركة يُرجع صفوف شركة الجلسة فقط.
   - استعلام بلا شركة مضبوطة لا يُرجع شيئًا.
   - محاولة الكتابة في شركة أخرى ترفضها قاعدة البيانات.
4. **قيود في قاعدة البيانات نفسها.**
   - مفاتيح أجنبية مركّبة `(user_id, company_id)` تمنع أي صف من الإشارة لمستخدم من شركة أخرى. مثال: `audit_logs_actor_same_company_fk` و`clients_owner_same_company_fk`.
   - صلاحيات على مستوى العمود: دور التطبيق يحدّث أعمدة الأعمال فقط، فلا يستطيع نقل وحدة أو عميل لشركة أخرى أو تغيير مالك العميل، ولا يملك `DELETE` عليهما أصلًا.

الإثبات في اختبارات التكامل ([`tenant-isolation`](tests/integration/tenant-isolation.test.ts) و[`units`](tests/integration/units.test.ts) و[`clients`](tests/integration/clients.test.ts)):
- مدير شركة يرى أحداث شركته ووحداتها وعملاءها فقط، حتى مع `companyId` مُهرّب في الرابط أو في النموذج.
- RLS تحجب بقية الشركات، وعملاء المندوبين الآخرين، حتى مع استعلام بلا فلتر.
- الكتابة في شركة أخرى، أو باسم مندوب آخر، مرفوضة من قاعدة البيانات.

**حدّ معروف:** جداول الدخول (`users`، `sessions`، `login_attempts`) بلا RLS، لأن الدخول يسبق معرفة الشركة. الوصول إليها محصور في `src/server/auth/`، ودور التطبيق لا يملك عليها إلا ما يحتاجه (`users`: قراءة فقط).

### الصلاحيات

- **مصدر واحد:** [`src/lib/permissions.ts`](src/lib/permissions.ts)، منقول من جدول الأدوار في المتطلبات. اختبار يعيد صياغة كل سطر من الجدول ويقارنه به.
- **Server Actions:** تُبنى كلها بـ `createAction`، وتمر بالترتيب: الجلسة ← الصلاحية ← مخطط الإدخال ← المعالج داخل `withTenant`.
- **الصفحات:** تستدعي `requirePermission`. الدور غير المسموح له يحصل على 404 وليس 403، فلا يتأكد حتى أن الصفحة موجودة.
  - الفحص يكون خارج أي حدود `loading.tsx`: داخلها تكون الاستجابة بدأت بـ 200، فيظهر محتوى 404 تحت حالة 200. لذلك سجل التدقيق يفحص في `layout.tsx` القسم، والوحدات والعملاء بلا `loading.tsx` أصلًا: الصفحة تفحص الصلاحية وتجلب السجل أولًا، وحالة التحميل لجداول القوائم `Suspense` داخل الصفحة. `scripts/smoke.sh` يفحص الحالة نفسها.
- **داخل الشركة، العميل لمندوبه:** المندوب يرى ويعدّل عملاءه فقط. معرّف عميل مندوب آخر يُجاب بـ 404 كمعرّف غير موجود، في الاستعلام وفي سياسة RLS معًا.
- **`proxy.ts` لا يتحقق من شيء.** الاعتماد على الـ middleware وحده هو بالضبط ما تجاوزته CVE-2025-29927.

## الحجز والعقود والأقساط والدفعات

### الحجز: 72 ساعة، ومندوب واحد فقط

- **التزامن:** الحجز يقفل صف الوحدة (`SELECT … FOR UPDATE`) قبل أن يقرأ حالتها. مندوبان في اللحظة نفسها يصطفّان على القفل: الأول يجدها متاحة فيحجزها، والثاني ينتظر ثم يجدها محجوزة فيأخذ «الوحدة محجوزة الآن لعميل آخر. تعود متاحة تلقائيًا عند انتهاء مدة الحجز.».
- **شبكة أخيرة:** فهرس فريد جزئي على `reservations(unit_id) WHERE status = 'active'`، فلا يوجد حجزان نشطان للوحدة حتى لو تجاوز شيء القفل.
- **المدة في قاعدة البيانات:** `expires_at = created_at + 72 ساعة` قيد `CHECK`، والوقتان من `now()` في القاعدة لا من ساعة الخادم.
- **الانتهاء بلا تدخل، على مستويين:**
  1. **كل قرار يفحص الساعة بنفسه تحت القفل:** الحجز ومسودة العقد والاعتماد. حجز انتهت مدته لا يُعتمد عقده ولو لم يمر أي منظّف بعد، ووحدته تُحجز لمندوب آخر مباشرة.
  2. **كل قراءة تُنهي ما حان وقته أولًا** (قوائم الوحدات والحجوزات وصفحاتها)، ومنظّف داخل التطبيق كل 60 ثانية (`src/instrumentation.ts`). الاثنان يستدعيان دالة واحدة في القاعدة `expire_due_reservations()` تتخطى بـ `SKIP LOCKED` أي وحدة يعمل عليها طلب الآن.
- **العدّ التنازلي في الصفحة** يبدأ من وقت الخادم ويتحدّث كل ثانية، وعند الصفر يطلب الصفحة من الخادم مرة واحدة: الخادم هو من يقرر أن الحجز انتهى، لا ساعة المتصفح.
- **المندوب لا يحجز إلا لعميله:** مفتاح أجنبي مركّب `(client_id, reserved_by, company_id) → clients(id, owner_user_id, company_id)`.

### العقد: مسودة من المندوب، واعتماد من المحاسب

- **المسودة** من حجز نشط للمندوب نفسه، بسعر الوحدة وقت الإنشاء. **السعر النهائي** بين 95% و100% من سعر الوحدة: في الخدمة (مع رسالة تذكر المدى بجوار الحقل) وفي قيد `CHECK` بالقاعدة.
- **المندوب يعدّل مسودته** ما دامت مسودة وحجزها قائمًا، ويُعاد بناء الجدول في كل تعديل. كل تعديل يرفع `revision`.
- **الاعتماد في معاملة واحدة:** يقفل الوحدة ثم الحجز ثم العقد (الترتيب نفسه في كل المسارات، فلا deadlock)، ثم يغيّر العقد إلى «معتمد» والحجز إلى «تحوّل إلى عقد» والوحدة إلى «مباعة»، ويكتب سجل التدقيق. أي فشل يلغي الأربعة معًا.
- **المحاسب يعتمد ما رآه:** النموذج يرسل `revision` الصفحة. إن عدّل المندوب المسودة بعد أن فتحها المحاسب، يُرفض الاعتماد ويُطلب منه مراجعتها من جديد.
- **بعد الاعتماد لا يتغير شيء:** trigger يرفض أي تعديل على عقد معتمد أو على جدوله، حتى من مالك الجداول. ووقت الاعتماد `approved_at` تكتبه القاعدة لا التطبيق.

### جدول الأقساط

- **الحساب:** `(السعر النهائي − الدفعة الأولى) ÷ عدد الأقساط`، بالهللة. الباقي من القسمة يوزَّع **هللة واحدة على كل قسط من الأقساط الأولى**، فالمجموع يساوي السعر النهائي بالهللة دائمًا، والفرق بين أي قسطين هللة على الأكثر.
- **الدفعة الأولى** صف في الجدول نفسه (رقم 0) مستحقة في تاريخ بداية العقد، فتُدفع وتتأخر كأي قسط. إن كانت صفرًا فلا صف لها.
- **القسط رقم k مستحق بعد k شهر من تاريخ البداية**، والشهر الأقصر يأخذ آخر يوم فيه:
  - عقد يبدأ **31 يناير**: 28 فبراير (29 في السنة الكبيسة)، ثم **31 مارس**، ثم 30 أبريل، ثم 31 مايو.
  - التاريخ يُحسب **من تاريخ البداية في كل مرة** لا من القسط السابق. لو حُسب من السابق لصار 31 يناير ← 28 فبراير ← 28 مارس ← 28 أبريل…، فينزاح يوم الاستحقاق للأبد بعد أول شهر قصير.
- **الحالة تُشتق ولا تُخزَّن:** مدفوع (لا شيء متبقٍ)، متأخر (فيه متبقٍ وتاريخه قبل اليوم بتوقيت الرياض، **حتى لو دُفع جزء منه**)، مدفوع جزئيًا (دُفع جزء ولم يحن موعده)، لم يحن موعده (لم يُدفع منه شيء). القسط المستحق اليوم ليس متأخرًا بعد.
- المنطق كله في `src/domain/` (دوال نقية)، واختبارات الوحدة تغطيه بلا قاعدة بيانات.

### الدفعات

- **المحاسب يسجّل أي مبلغ،** ويوزَّع على **أقدم الأقساط غير المدفوعة أولًا** (بتاريخ الاستحقاق ثم الرقم)، فيصبح القسط مدفوعًا أو مدفوعًا جزئيًا.
- **لا تتجاوز المتبقي:** الخدمة ترفض برسالة تذكر المتبقي بجوار الحقل. وقيد `paid ≤ amount` على كل قسط يرفض في القاعدة أي توزيع زائد.
- **دفعتان على العقد نفسه في الوقت نفسه** تصطفّان على قفل صف العقد، فالثانية تقرأ الرصيد بعد الأولى.
- **النقرة المزدوجة أو إعادة إرسال الطلب لا تنشئ دفعتين:** النموذج يحمل `idempotencyKey` يُولَّد مع الصفحة، وفريد في القاعدة لكل شركة. الإرسال الثاني بالمفتاح نفسه يُرجع الدفعة الأولى («هذه الدفعة سُجِّلت من قبل، ولم تُسجَّل مرة ثانية»). والزر يتعطل أثناء الإرسال، لكنه تحسين للواجهة لا الضمان.
- **الدفعة لا تُعدَّل ولا تُحذف:** دور التطبيق لا يملك `UPDATE`/`DELETE` على `payments` و`payment_allocations`، و trigger يرفضهما حتى من المالك.
- **المدفوع على كل قسط يكتبه trigger وحده** عند إدراج التوزيع، وقيد مؤجل حتى الـ commit يتحقق أن كل دفعة وُزّعت بمبلغها كاملًا: لا مال مسجَّل بلا قسط، ولا قسط مدفوع بلا دفعة.
- **التسجيل في معاملة واحدة:** الدفعة وتوزيعها وتحديث الأقساط وسجل التدقيق.

### سجل التدقيق

محاولات الدخول (الناجحة والفاشلة)، وتغيير سعر الوحدة (القديم والجديد)، واعتماد العقد (العميل والسعر النهائي)، وتسجيل الدفعة (المبلغ والمتبقي بعدها). كل قيد يُكتب **داخل معاملة العملية نفسها**، فلا عملية بلا قيد ولا قيد بلا عملية.

## الافتراضات

- **البريد فريد على مستوى النظام كله.** شاشة الدخول لا تطلب اختيار شركة.
- **الجلسة 12 ساعة متجددة:** تتمدد عند الاستخدام إذا بقي أقل من نصفها. الخروج يحذفها من قاعدة البيانات.
- **حد المحاولات:**
  - 5 محاولات فاشلة لكل بريد خلال 15 دقيقة، تُحسب من آخر دخول ناجح.
  - البريد غير الموجود يُقفل بنفس الطريقة وبنفس الرسالة، فالقفل لا يكشف وجود الحساب.
  - حدّ إضافي لكل IP (20 محاولة) يعمل فقط عند `TRUST_PROXY=true`. App Router لا يوفّر عنوان الاتصال، و`X-Forwarded-For` يكتبه العميل كما يشاء، فلا يُصدَّق إلا خلف proxy نديره (ويُؤخذ آخر عنوان أضافه).
- **محاولة دخول فاشلة لبريد غير موجود** تُسجَّل في سجل التدقيق بلا شركة، فلا يراها أي مدير. المحاولة لبريد موجود تظهر في سجل شركته.
- **الكوكي `Secure` على `http://localhost`:** Chrome و Firefox يعتبران localhost سياقًا آمنًا فيحفظان الكوكي. Safari قد لا يحفظها، لذلك التشغيل المحلي على Chrome أو Firefox. أي نشر حقيقي يكون عبر HTTPS.
- **كلمات مرور قاعدة البيانات في `docker-compose.yml`** قيم افتراضية محلية للتقييم فقط، ويمكن تجاوزها بمتغيرات البيئة (`.env.example`).
- **قراءة سجل التدقيق للمدير فقط،** كما في جدول الأدوار.
- **المحاسب يقرأ الوحدات والعملاء** (يحتاجهم للعقود والدفعات) **ولا يعدّل أيًّا منهما.** المدير يرى كل عملاء الشركة لكن لا يضيف ولا يعدّل عميلًا، فهذا للمندوب في جدول الأدوار.
- **العميل ملك المندوب الذي أضافه، ولا ينتقل.** رقم الجوال فريد لكل مندوب لا لكل شركة: مندوبان قد يعرفان الشخص نفسه.
- **لا حذف للوحدات ولا للعملاء:** المتطلبات لا تذكره، والعقود ستشير إليهم. دور التطبيق لا يملك `DELETE` عليهما.
- **المشروع نص حر على الوحدة،** كما في المتطلبات، ورقم الوحدة فريد داخل المشروع في الشركة.
- **السعر** حتى 999,999,999,999.99 ر.س بخانتين عشريتين على الأكثر وأكبر من صفر. النماذج تقبل الأرقام العربية (٠-٩) والفاصلة العشرية العربية وفواصل الآلاف.
- **الترتيب الافتراضي** للقوائم: الأحدث إضافة أولًا.
- **الحجز:** لا يُلغى يدويًا (الإلغاء غير مطلوب)، وينتهي وحده بعد 72 ساعة.
- **عقد واحد لكل حجز،** وتُحفظ معه نسخة من سعر الوحدة وقت إنشائه. المدير يرى العقود ولا يعتمد، كما في جدول الأدوار.
- **تاريخ بداية العقد** بين 30 يومًا مضت وسنة قادمة، و**عدد الأقساط** من 1 إلى 120 شهرًا. الدفعة الأولى أقل من السعر النهائي، ويمكن أن تكون صفرًا.
- **«اليوم» بتوقيت الرياض** في الاستحقاق والتأخر، أيًّا كانت منطقة الخادم.
- **الحجز مُلزم حتى الاعتماد:** مسودة انتهى حجزها تبقى للسجل ولا تُعتمد، ويلزم حجز جديد.
- **المحاسب يسجّل الدفعات على العقود المعتمدة فقط،** ولا وسيلة دفع ولا إيصال (غير مطلوبين).

## الأمان — أهم 3 مخاطر

### 1. تسريب بيانات بين الشركات

الخطر الأكبر في نظام Multi-tenant: مستخدم مسجّل يغيّر معرّفًا في رابط أو طلب فيرى بيانات شركة أخرى.

**المعالجة:** الطبقات الأربع الموضحة في [البنية](#كيف-يُضمن-أن-كل-استعلام-مقيّد-بشركة-الجلسة)، مع اختبار تكامل يثبتها.

### 2. كسر الصلاحيات داخل الشركة

مندوب يعتمد عقدًا أو يعدّل سعرًا بإرسال الطلب يدويًا بعد أن أُخفي الزر عنه.

**المعالجة:**
- الصلاحيات تُفرض في الخادم على كل Action وكل صفحة من خريطة واحدة مختبرة.
- الحقول غير المسموح بها تُرفض قبل أن تصل للمعالج.
- قواعد العمل الحساسة محكومة في قاعدة البيانات أيضًا: تغيير السعر وانتقالات الحالة (trigger)، وملكية العميل والحجز والعقد (RLS). المندوب لا يرى حجوزات غيره ولا عقودهم ولا أقساطهم، وسياسات RLS لا تقبل الاعتماد وتسجيل الدفعة إلا من المحاسب.
- اختبار يحاول فيه المندوب أن يعتمد مسودته بـ SQL مباشر بدور التطبيق، فترفضه قاعدة البيانات.

### 3. خطأ في المال تحت التزامن أو إعادة الإرسال

حجز الوحدة لعميلين، أو دفعة مسجّلة مرتين، أو مجموع مدفوع يتجاوز العقد، أو عقد معتمد تتغير شروطه بعد اعتماده. أخطاء صامتة لا تظهر في التجربة اليدوية، وثمنها مال حقيقي.

**المعالجة:**
- المال عدد صحيح بالهللة في كل طبقة، ولا يمر بعدد عشري ثنائي.
- كل قرار مالي تحت قفل صف (الوحدة، ثم العقد)، بترتيب أقفال ثابت.
- `idempotencyKey` فريد للدفعة، وفهرس فريد للحجز النشط، وعقد واحد لكل حجز.
- القواعد نفسها في قاعدة البيانات أيضًا: حد الخصم، و`paid ≤ amount`، واكتمال توزيع الدفعة عند الـ commit، وتجميد العقد المعتمد، والدفعات للإضافة فقط.
- اختبارات تكامل بطلبات متزامنة حقيقية تثبت كل ما سبق.

### ضوابط أخرى

- **الاستيلاء على حساب أو جلسة:**
  - Argon2id، وحد محاولات دقيق تحت التزامن.
  - رسالة خطأ وزمن استجابة متطابقان للبريد الموجود وغير الموجود (تحقق مقابل hash وهمي).
  - كوكي `HttpOnly; Secure; SameSite=Lax`، ولا توكنات في `localStorage`. التوكن لا يُخزّن إلا مجزّأ، والخروج يبطل الجلسة في الخادم.
  - CSP بـ nonce و `strict-dynamic` تقلل سطح XSS.

- **سجل التدقيق للإضافة فقط:** دور التطبيق لا يملك `UPDATE`/`DELETE` عليه، و trigger يرفضهما حتى من مالك الجدول.
- **الملاحظات الحرة لا تُعرض إلا نصًا:** React يهرّبها، ولا يوجد `dangerouslySetInnerHTML` في المشروع. تُخزَّن كما كُتبت، والـ smoke test يتحقق من أنها تعود مُهرّبة.
- **رسائل الخطأ للمستخدم عامة،** والتفاصيل في سجلات `pino` مع حجب كلمات المرور والكوكيز.
- **ترويسات أمان HTTP:** `nosniff` و `frame-ancestors 'none'` و `Referrer-Policy` و `Permissions-Policy` و HSTS، بدون `X-Powered-By`.
- **`npm audit --audit-level=high`** في الـ CI.

## ما لم يُنجز

- **خارج النطاق المحدد:** إلغاء العقد، ولوحة التحكم، والتصدير، ورفع الملفات، ومراحل CRM، وإدارة المستخدمين، واستعادة كلمة المرور.
- **إلغاء الحجز يدويًا:** غير مطلوب، فالحجز ينتهي وحده.
- **المنظّف الدوري داخل عملية التطبيق.** يكفي لنسخة واحدة، ومع عدة نسخ يبقى صحيحًا (`SKIP LOCKED`، والقرار يفحص الساعة بنفسه) لكنه مكرر. في الإنتاج: `pg_cron` أو worker مستقل.
- **اختبار E2E واحد** للمسار الأساسي. حالات الرفض والتزامن مغطاة في اختبارات التكامل.
- **لا إشعارات** (اقتراب استحقاق قسط، أو انتهاء حجز).
- **الحد بالـ IP مقفول افتراضيًا.** App Router لا يعطي عنوان الاتصال الحقيقي، و`X-Forwarded-For` يكتبه العميل كما يشاء، فتصديقه بلا proxy نديره يعني أن المهاجم يختار عنوانه بنفسه. لذلك لا يعمل إلا مع `TRUST_PROXY=true`. وبدونه يبقى حد البريد وحده، فيمكن تجربة كلمة مرور شائعة على بريدات كثيرة (password spraying). في الإنتاج: حد للطلبات على الـ reverse proxy نفسه، ثم `TRUST_PROXY=true`.
- **قفل حساب معروف بخمس محاولات.** من يعرف بريد المحاسب يستطيع أن يقفل دخوله 15 دقيقة بخمس محاولات خاطئة، ويكررها. الحل الذي كنت سأنفذه: تأخير متصاعد بدل القفل الكامل، والقفل لكل (بريد + IP) خلف proxy موثوق، وتنبيه للمدير عند تكرار القفل.
- **تحديث الصفحة ثم إعادة إرسال الدفعة.** مفتاح الدفعة يُولَّد مع الصفحة، فالضغط مرتين أو إعادة إرسال النموذج نفسه لا يكرر الدفعة. لكن من يحدّث الصفحة ثم يرسل من جديد يحصل على مفتاح جديد ودفعة ثانية. كنت سأحفظ المفتاح في الصفحة حتى تنجح الدفعة (`sessionStorage`)، وأعرض تحذيرًا قبل تسجيل دفعة بنفس المبلغ على نفس العقد خلال دقائق.
- **`proxy.ts` يمدّد الكوكي دون أن يتحقق منها.** الـ proxy يعيد ضبط أي توكن يصله مع GET ليمدّد مدته، فتوكن ألغاه الخروج يعود في الرد. لا يفتح شيئًا: الجلسة محذوفة من قاعدة البيانات وكل طلب به يُحوَّل إلى `/login`. الإصلاح: التمديد فقط حيث تُقرأ الجلسة من قاعدة البيانات، ومسح الكوكي عندما تُرفض.
- **الاعتماد وتسجيل الدفعة يحتاجان JavaScript.** الزر يفتح نافذة تأكيد قبل الإرسال، فبلا JavaScript لا يحدث شيء. باقي النماذج تعمل بدونه. والخادم لا يعتمد على النافذة: الطلب نفسه يُفحص كاملًا في الخدمة، واختبارات التكامل تغطيه بلا واجهة.
- **صفحات التفاصيل بلا حالة تحميل.** القوائم تعرض هيكل الجدول داخل `Suspense` أثناء الجلب، والأزرار تعرض «جارٍ…» أثناء الإرسال. أما صفحة الوحدة أو الحجز أو العقد فتظهر عند اكتمالها: `loading.tsx` فوقها يجعل `notFound()` يعود بـ 200 بدل 404، والفحص فيها الآن. كنت سأنقل الفحص إلى `layout.tsx` لكل `[id]` ثم أضيف `loading.tsx` تحته، كما في سجل التدقيق.

## أدوات الذكاء الاصطناعي

استخدمت Claude Code في التخطيط وكتابة معظم الكود والاختبارات. راجعت المنطق الأساسي (الحجز، الأقساط، الدفعات، العزل، الصلاحيات) وأستطيع شرحه وتعديله.

بالتفصيل:
- تقسيم العمل إلى مراحل.
- مراجعة القرارات الأمنية.
- في الحجز والعقود والدفعات: تصميم القيود والـ triggers وسياسات RLS، واختبارات التزامن. اختبارات الدفعات كشفت خطأً حقيقيًا في trigger التحقق من اكتمال التوزيع (`plpgsql` يحلّ كل حقل في تعبير `CASE` قبل اختيار الفرع)، وأُصلح قبل أي دمج.
- التحقق اليدوي من المسار في المتصفح على `localhost` بحسابات التجربة.
